1. Overview — What this flow really is

An ACH payroll credit run is the most common business payment in the United States. When you receive your salary on a Friday morning by direct deposit, you are receiving the credit leg of a NACHA-format ACH batch that was transmitted by your employer's payroll provider 48–72 hours earlier.

From the bank's perspective, this is a file-based, batch, deferred-net-settlement (DNS) EDI flow. The bank is the ODFI (Originating Depository Financial Institution) for the originating company, and the funds will land at thousands of RDFIs (Receiving DFIs) across the United States via either of the two ACH operators: FedACH (Federal Reserve) or EPN (The Clearing House Electronic Payments Network).

Who's involved

  • Originator — the retail company (employer)
  • Third-Party Sender (TPS) — the payroll vendor (e.g., ADP, Gusto)
  • ODFI — the originator's bank
  • ACH Operator — FedACH or TCH EPN
  • RDFI — each employee's bank
  • Receiver — each employee

What moves

  • One NACHA file, fixed-width, 94 characters per record
  • One file → one or many Batches
  • Each batch → many Entry Detail (06) records
  • Optional Addenda (07) records per entry
  • Plus Batch Control (08) and File Control (09) totals

When it happens

  • Day -2, 16:00 ET — payroll vendor → ODFI inbox
  • Day -1, AM — ODFI processes, delivers to operator
  • Day 0 (Friday) — operator distributes to RDFIs
  • Day 0, 09:00 ET — RDFIs post to employee accounts
  • Day +1 → Day +60 — return / NOC window depending on R-code

Key concepts you must understand on Day 1

ConceptPlain-English MeaningWhy It Matters in Testing
SEC CodeStandard Entry Class — tells the RDFI how the entry was authorized. PPD = consumer pre-authorized (most payroll). Other common: CCD, WEB, TEL, CTX, IAT.Different SEC codes have different return windows and Reg E protections. PPD allows R10/R11 returns up to 60 days.
Service Class CodeTells the operator the batch type. 200 = mixed credits & debits, 220 = credits only, 225 = debits only.A payroll batch must be 220. Any 225 in a payroll file is a defect.
Transaction Code2-digit code per entry. 22 = checking credit, 32 = savings credit, 23/33 = pre-notification (zero-dollar).Mismatch with Service Class causes the entire batch to reject.
Effective Entry DateThe date funds should post at the RDFI. Field on the Batch Header.Must be a banking day, must be within the operator's allowed window (1-2 banking days forward; same-day for SDA).
Trace Number15-digit unique key per entry: ODFI 8-digit routing prefix + 7-digit sequence.This is your correlation key. Returns reference it. Sterling persists it as the join column.
Hash & TotalsRouting-number hash, debit total, credit total, entry/addenda count — repeated on Batch Control and File Control.If totals don't match, the entire file is rejected. Top-five real-world defect.
Same-Day ACH (SDA)Three additional same-day windows (10:30, 14:45, 16:45 ET cut-offs as of 2026), per-transaction $1M cap.Late-running payroll often gets sent SDA. Test cut-off boundaries hard.
Pre-Notification (Pre-Note)Zero-dollar entry sent 3 banking days before the first live entry to verify account.If the RDFI rejects the pre-note, the live entry must be held.
One-line summary: a NACHA payroll run is a fixed-width batch file that travels SFTP→ODFI→Operator→RDFI on a multi-day deferred-net cycle, governed by NACHA Operating Rules and policed by the Federal Reserve, with a return window of up to 60 days for consumer entries.

2. Business Context — The real-world story

The Originator's view (the retailer)

"Acme Mart" is a US retail chain with 12,000 employees across 31 states. Bi-weekly pay date is every other Friday. Acme uses a payroll vendor (the Third-Party Sender) that:

  • Computes gross-to-net for every employee on Tuesday (Day -3).
  • Locks the file at 14:00 ET Wednesday (Day -2) after Acme's HR sign-off.
  • Encrypts (PGP) and SFTP-uploads the NACHA file to Acme's bank by 16:00 ET Wednesday.

The bank in this scenario is a Tier-2 US regional bank ("FirstNorth Bank") acting as the ODFI. The bank uses IBM Sterling B2B Integrator 6.x as its file-ingestion and routing platform, and Open Payments Framework / FIS / Finastra (or in-house) as its core ACH engine for Fed delivery.

Why a bank uses Sterling B2Bi for this

  • Multi-protocol secure ingestion (SFTP, FTPS, AS2, HTTPS) with PGP & per-partner mailboxes.
  • Per-partner schedules, throttles, and SLA monitors.
  • Pre-validation maps that reject malformed files at the perimeter before they touch the core ACH engine.
  • End-to-end correlation (file → batch → entry → return) with audit trail.
  • Operator dashboards for the Payments Ops team.

What can go wrong (and routinely does)

  • File totals mismatch — entire file rejected.
  • OFAC SDN hit on a beneficiary name → batch held, must be reviewed within 24 hours.
  • Effective entry date is a Federal holiday → batch warehoused or rejected.
  • One employee changed banks last month — old account closed → R02 / R03 return.
  • Duplicate file submission after operator outage — risk of double-pay.
  • Insufficient pre-funding on Acme's account — ODFI risk decision.

3. NACHA File Structure — The format, byte by byte

A NACHA file is a plain-text, fixed-width, ASCII file. Every record is exactly 94 characters, terminated by CRLF. Lines are blocked in groups of 10 (the "blocking factor"); if the last block is short, it is padded with 9's — a record full of nines.

The hierarchy

FILE HEADER (1)
  └── BATCH HEADER (5)
       └── ENTRY DETAIL (6)
             └── ADDENDA (7)   [optional, depends on SEC code]
       └── ENTRY DETAIL (6)
       └── ...
       └── BATCH CONTROL (8)
  └── BATCH HEADER (5)
       └── ...
  └── FILE CONTROL (9)
  └── (optional padding "999...")

Record types — what each line means

Memorize this rule: File Control totals = Σ Batch Control totals = Σ Entry Detail amounts. If any of those three relationships is off by even one cent, the operator rejects the entire file. This is the single most common reason a payroll run fails on Wednesday night.

Business Process (BP) shape — pseudocode

<process name="Inbound_NACHA_PayrollVendor">
  <sequence>
    <!-- 1. File arrived in mailbox; BP invoked by mailbox event -->
    <operation name="GetFromMailbox">
      <participant name="MailboxExtractAbstractService"/>
    </operation>

    <!-- 2. Decrypt PGP -->
    <operation name="PGPDecrypt">
      <participant name="PGPPackageService"/>
      <output message="DecryptIn">
        <assign to="profile_id">ACMEPAY_PGP</assign>
      </output>
    </operation>

    <!-- 3. Pre-validate filename + duplicate check -->
    <operation name="DuplicateCheck">
      <participant name="JDBCAdapter"/>
      <output message="DupCheck">
        <assign to="query">SELECT 1 FROM nacha_file_log WHERE file_hash=? AND received_dt>sysdate-7</assign>
      </output>
    </operation>
    <choice>
      <onMessage condition="duplicate_found">
        <operation name="RaiseError">...send alert, stop...</operation>
      </onMessage>
    </choice>

    <!-- 4. Translate NACHA → canonical XML -->
    <operation name="TranslateNACHA">
      <participant name="TranslationService"/>
      <output message="TransIn">
        <assign to="map_name">NACHA_INBOUND_PPD_v3</assign>
      </output>
    </operation>

    <!-- 5. Validate totals, dates, SEC, OFAC pre-flag -->
    <operation name="ValidateBatchTotals">
      <participant name="XSLTService"/>
    </operation>

    <!-- 6. Persist file/batch/entry rows -->
    <operation name="PersistEntries">
      <participant name="LightweightJDBCAdapter"/>
    </operation>

    <!-- 7. Hand off to core ACH engine -->
    <operation name="PublishToCore">
      <participant name="MQAdapter"/>
      <output message="MqOut">
        <assign to="queue">ACH.OUTBOUND.CORE</assign>
      </output>
    </operation>

    <!-- 8. Acknowledge to vendor mailbox: ACK file -->
    <operation name="WriteACK">
      <participant name="MailboxAddService"/>
    </operation>

  </sequence>
  <onFault>
    <sequence>
      <operation name="LogError">...</operation>
      <operation name="EmailOps">...</operation>
      <operation name="WriteNAK">...</operation>
    </sequence>
  </onFault>
</process>

Senior dev tip: never let the NACHA inbound map be the single source of truth for validation. Put schematic validation in the map (lengths, field types, mandatory presence), but put business validation (totals, dates, SEC compatibility, duplicate detection) in a separate XSLT or stored procedure. This gives QA a clean place to inject test cases and keeps the map maintainable.

7.3   Functional tests FUN

Field-, record-, and rule-level tests. Largest section.

P0 FUN File Header — invalid record size
Submit file with record size 095. Expected: reject with error VAL-001 Record Size must be 094; NAK file written.

P0 FUN Routing Check Digit invalid
Set RDFI routing 11100002 with check digit 9 (correct is 5). Expected: entry rejected; rest of batch processed; entry recorded with status RJCT-RTG.
P1 FUN Effective Entry Date is a Federal holiday (e.g., Jul 4)
Expected: warehouse to next banking day OR reject per ODFI policy; alert raised; UI shows revised effective date.
P1 FUN Effective Entry Date in the past
Expected: reject with STALE_DATE if > 2 banking days old; otherwise auto-shift per policy.
P0 FUN Batch Control entry count mismatch
Batch has 3 entries but Batch Control says 4. Expected: entire file rejected; BATCH_COUNT_MISMATCH.
P0 FUN File Control hash mismatch
Manually corrupt the entry hash on Type 9. Expected: file reject; alert.

P1 FUN Pre-notification (TxnCode 23/33) zero-dollar entry — allowed

Expected: processed for next-day delivery to operator.

A library of 50+ historical NACHA files (anonymized) with known-good canonical XML output. After any change, re-translate and diff.
P1 REG All 8 SEC code variants
PPD, CCD, WEB, TEL, CTX, IAT, ARC, BOC — verify each routes correctly and either translates (supported) or rejects with the right code (unsupported).
P2 REG Full R-code matrix (R01–R85)
For each return code defined in NACHA, simulate a return and verify Sterling's return-handling map produces the right downstream XML.

7.7   Reconciliation tests RCN

End-of-day and end-of-cycle accounting controls.

P0 RCN File-level recon: vendor totals = Sterling totals = core totals
For every file ingested, verify file.total_credit matches the sum the core engine accepted and the operator confirmed.
P0 RCN Daily Fed settlement recon
ODFI's Fed master account net debit/credit at end of settlement window matches sum of Sterling's outbound batches for that day.
P1 RCN Returns recon
Sum of returns received in 60 days = sum of debits to corporate's account for those R-codes. Off-by-one or off-by-cent must alarm.
P1 RCN Vendor SLA recon
Files received per SLA, files processed per SLA, ACK files sent per SLA — daily report.

7.8   Performance & volume tests PRF

P1 PRF Peak load: 50,000 entries in single file
Verify BP completes within SLA (e.g., 15 min); no memory leaks; DB write throughput acceptable.
P1 PRF Concurrency: 10 vendors uploading simultaneously
No file mix-up between mailboxes; per-vendor BP isolation; node pool sized correctly.
P2 PRF Soak test: 4-hour continuous file submission at quarter-end peak
No degradation, no leaks, no DB lock escalation.
P2 PRF Stress: 1M entries (10× peak)
Acceptable failure mode is graceful slowdown or file split, not data loss.

7.9   Security tests SEC

P0 SEC OFAC SDN screening hit
Submit file with synthetic "OSAMA BIN LADEN" name. Expected: entry held; alert to Financial Crimes; never released without manual review; never auto-debit corporate.
P0 SEC SFTP authentication failure does not write to mailbox
Wrong key. Connection refused; no partial file in staging.
P0 SEC PGP signature verification
File encrypted but unsigned (or signed by wrong key) → reject per policy.
P1 SEC File pollution / path traversal
Filename contains ../../. Expected: rejected at perimeter.
P1 SEC Replay attack: same file resubmitted
Identical SHA-256 hash within 7-day window. Expected: duplicate detection halts processing.
P1 SEC PII handling in logs
Verify account numbers and SSNs are masked in BP logs and audit trails.

7.10   UAT scenarios UAT

Run with the business owner (Treasury Mgmt or Cash Mgmt Ops). Each scenario must be acceptable to a non-technical sign-off.

P1 UAT Operations dashboard usability
Ops user can find a payroll run by company, date, or trace number within 60 seconds.
P1 UAT Notification clarity
Reject email contains: file name, vendor, reason, suggested next action. Reviewed and approved by business.
P1 UAT Manual reprocess workflow
Ops can re-trigger a previously rejected file after vendor fix. Audit trail preserved.

7.11   R-flow / return tests RFL

Returns are an entire sub-system. They are also where banks commonly lose money via failed match-back.

P0 RFL R01 Insufficient Funds — return matched and reversed
RDFI returns R01 within 2 banking days. Sterling matches by trace #, marks original entry RTN-R01, debits corporate's settlement account.
P0 RFL R02 Account Closed
Same as R01 but with R02 reason; verify proper code-list translation and statement narrative.
P0 RFL R03 No Account / Unable to Locate
Common in payroll when employee changed banks. Verify employee record flagged for HR follow-up.
P1 RFL R10 Customer Advises Unauthorized (consumer Reg E)
RDFI returns R10 anywhere from day 1 to day 60. Verify Sterling accepts late returns up to the 60-day Reg E window; alerts compliance; debits corporate; documents indemnification flow.
P1 RFL R11 Customer Advises Improperly Authorized
Similar to R10. Test 60-day window boundary precisely.
P1 RFL NOC (Notification of Change) C01 Incorrect Account Number
RDFI corrects account #. Sterling must update Acme's record-of-change for next pay run; not a return, no debit; pay this run still posts.
P1 RFL Return arrives for an entry Sterling has no record of
Orphan return. Expected: route to investigation queue; do not auto-reverse anything; alert ops.
P2 RFL Late return outside 60-day window
Return on day 61. Expected: reject with reason "outside-window"; do not debit corporate.

Test data factory — what to build first

Before writing test cases, build a generator that produces parameterized NACHA files. Suggested parameters:

  • --entries N — count
  • --sec PPD|CCD|WEB|...
  • --effective-date YYYY-MM-DD
  • --include-prenote
  • --corrupt totals|hash|date|service-class — for negative tests
  • --ofac-hit — inject a synthetic SDN-list name
  • --routing-error N — inject N invalid check digits
  • --seed S — deterministic for regression

Investing 2 weeks in this factory pays back forever. Open-source moov-io/ach (Go) is an excellent starting point.

QA priority advice: on a typical bank delivery, 30-40% of all defects raised against this flow are about returns and reconciliation, not about the happy path. Spend your test effort proportionally.

8. Real-World Scenarios

These are not synthetic. Every scenario below has played out in production at multiple US banks. As a tester or BA, knowing them up-front is the difference between "good enough" and "production-ready".

Scenario 1 — Friday before a long weekend, file held by OFAC

The vendor delivers the bi-weekly payroll on Wednesday before Memorial Day weekend. One employee's last name happens to fuzzy-match an OFAC SDN. Compliance only reviews on next business day (Tuesday). Without a clear policy, 12,000 employees miss Friday paychecks.

What good design does: single-name OFAC hits in a 12,000-row PPD file are isolated to that one entry. The other 11,999 release on time. The held entry waits in a "Compliance Hold" queue.

What QA tests: partial-release behavior; queue UI for compliance officer; SLA timer on hold; auto-release vs auto-reject if no review within X hours.

Scenario 2 — Vendor sends the same file twice "by mistake"

An ops person at the payroll vendor re-uploads Wednesday's file at 18:00 because they "weren't sure it went through". Without dedup, 24,000 credits go out and Acme is double-debited $7M.

What good design does: dedup by content hash (SHA-256 of file bytes) within a sliding window; reject identical resubmits; allow operator-initiated reprocess only via a separate authorized BP.

What QA tests: exact duplicate; near-duplicate (one byte changed); duplicate after vendor "correction"; clearing of dedup window after 7 days.

Scenario 3 — Wrong fiscal year in Effective Entry Date

Vendor's Date library defaults YY=00 in January. File submitted Jan 3, 2026 has Effective Entry Date 950109 (1995!). Some lax operators silently warehouse this for the next valid window; modern systems reject.

What good design does: reject any effective entry date > 2 banking days in past or > 7 days in future; alert.

What QA tests: boundary years 99→00, 24→25, leap-day Feb 29, December → January cross.

Scenario 4 — RDFI returns R10 on day 59

An employee disputes the deposit (claiming it was unauthorized — typically a fraud or domestic-abuse situation). RDFI files R10 on day 59. Some legacy ODFIs reject anything past 5 days; this violates Reg E.

What good design does: accept R10/R11 up to day 60, debit corporate, document, send to Financial Crimes for indemnification claim.

What QA tests: day 1, day 30, day 60, day 61 boundary; corporate ledger debit; alert to compliance; audit trail.

Scenario 5 — Same-Day ACH cap exceeded

A bonus run includes a $1.2M payment to an executive. Sent in the SDA window with an entry that exceeds the $1M per-tx cap. Operator rejects the entry, not the file.

What good design does: pre-flight check at Sterling layer that blocks any SDA-flagged entry above cap; suggest non-SDA window if amount allows.

What QA tests: $999,999.99, $1,000,000.00, $1,000,000.01 boundaries; SDA flag handling; mixed file with some SDA-eligible, some not.

Scenario 6 — Federal holiday calendar drift

Juneteenth (June 19) became a federal holiday in 2021. Banks that didn't update their holiday table either reject valid files or auto-warehouse files that should have processed.

What good design does: holiday calendar is a code list, sourced from Federal Reserve published calendar; refreshed annually; covered by a regression test.

What QA tests: all federal holidays for current and next year; Friday-into-Monday holidays; regional bank holidays (e.g., Patriot's Day in MA/ME).

Scenario 7 — Network outage at FedACH for 90 minutes

Real outage example: FedACH unavailable during the morning processing window. Files stack up in the operator queue. Some banks panic and switch to TCH EPN; others wait.

What good design does: Sterling tracks per-file state independently; on operator recovery, replays in correct order; never duplicates.

What QA tests: simulated operator outage of 30/60/120 minutes; queue depth alerting; replay correctness; manual operator instructions for ops team.

Scenario 8 — Pre-note success, but live entry rejected

Pre-note went through fine 10 days ago. The employee then closed and re-opened a different account. Live entry on the original account fails R02.

What good design does: pre-note success does not eliminate live-entry validation; treat them independently; flag pattern of "pre-note ok then live R02" as an emerging fraud signal.

What QA tests: separate prenote-pass + live-fail flow; alerting on suspicious patterns.
